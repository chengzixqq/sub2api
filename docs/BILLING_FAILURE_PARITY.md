# 失败请求计费（billing failure parity）

上游服务商对**失败/中断的请求**同样收费。本特性让 sub2api 对这类请求也计费，
避免站点自己承担这部分成本。

本文档面向**报表与账目使用者**，说明该特性引入的数据口径变化。

## 1. usage_logs.billing_provenance

新增字段，标记每一行用量的计费来源：

| 取值 | 含义 |
|---|---|
| `NULL` | 成功请求，用量来自上游真实 usage（绝大多数行） |
| `estimated` | 成功请求，但上游未返回 usage 帧，用量为本地估算 |
| `failed_upstream` | **失败**请求，但拿到了上游真实 usage |
| `failed_estimated` | **失败**请求，用量为本地估算 |

后两种是本特性新产生的行。它们对应真实发生的上游费用，因此
`actual_cost` 是真金白银，必须计入账目总额。

## 2. 请求数与金额的口径差异（重要）

**金额（cost / token 汇总）**：所有界面口径一致，均**包含**已计费的失败行。
这是刻意设计——这些行产生了真实上游支出，若排除会与总账对不上。

**请求数**：两处口径不同，这是已知且刻意的差异。

| 位置 | 是否计入已计费失败行 |
|---|---|
| 总览页「总请求数」/「今日请求数」 | **计入** |
| 分平台 / 分用户明细的请求数 | **不计入** |

原因：明细的请求数用于观察"成功请求量"，把失败行计入会让该视角失真；
而总览大盘取自物化聚合表 `usage_dashboard_daily`，其请求数为裸计数。

**因此总览的总请求数会略高于分平台明细的合计**，差额等于该时段已计费的失败请求数。
这不是数据错误。若需精确核对成功请求量，请以分平台/分用户明细为准。

> 补充：运维告警中的 `success_rate` / `error_rate` 指标**不受影响**——它们取自
> 独立的 `ops_metrics_hourly` 与 `ops_error_logs`，与 `usage_logs` 的请求数无关。

## 3. usage_logs.upstream_endpoint 归因口径变更

**变更时点：本特性上线。前后数据不可直接比较。**

变更前，API-Key 账号访问以下**专用入站端点**时，`upstream_endpoint` 会被错记成
`chat/completions` 或 `responses`（这些端点被当作文本补全面转发）：

- `embeddings`
- `images/generations`、`images/edits`
- `videos`、`videos/generations`、`videos/edits`、`videos/extensions`
- alpha search

变更后，它们各自保留真实的上游路径。

**影响范围**：仅该字段的**归因分布**。该字段不参与任何费用计算（已实证：它从未
出现在成本计算函数的入参或函数体内，只写入 `usage_logs` 行并供统计查询分组），
**金额零影响**。

**对报表的影响**：按 `upstream_endpoint` 分组的报表，在变更时点前后会出现口径断点——
变更前 `chat/completions` 偏高、专用端点偏低；变更后归因正确。做跨时段对比时请以
变更时点切分，或改用其它维度分组。

## 4. 计费的支配原则

实现遵循**宁可少算，不可多算**：任何无法确证上游已投递内容的情形，一律不计费。
具体地，判定"上游是否真的投递过推理内容"只信任 service 层在观测到上游第一帧真实
内容时设置的显式标记，默认为「未投递」。sub2api 自己写出的 keepalive ping 与错误
事件帧不会触发该标记，因此上游 200 后挂死、零 token 投递的请求不会被计费。
