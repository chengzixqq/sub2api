# 用户专属调度账号

管理员可针对“用户 + API Key 请求分组”设置账号策略。账号本身的可调度状态、模型支持、额度、限流和分组访问授权仍然生效；专属策略不赋予用户新的分组访问权。

## 策略

- **默认**：使用原有分组调度，但不使用标为“仅授权调度”的账号。
- **追加**：在原有普通候选上增加显式选择的账号。组外账号只对该用户在这个请求分组下生效，不改变它在原分组的行为。
- **指定名单**：只使用显式选择的账号。组内选择为空而组外追加非空时仍可用；整个名单为空或全部不可用时请求失败。分组新加入的账号不会自动进入名单。
- **恢复默认**：删除该用户的策略，不能用空指定名单代替。

账号可标记为“仅授权调度”，包括属于某分组或不属于任何分组的账号。它不会进入普通用户请求的默认候选，只有被显式选择时才有机会参与调度。首版组外授权只支持与目标单平台分组同平台的账号；默认工作区可直接使用，其他工作区必须处于启用状态，并持有该分组的有效授权。不支持复合分组跨组授权。已有上游请求和已提交的异步任务可完成；撤权阻止后续选号。

## 上线顺序

1. 先在所有管理实例关闭专属策略写入，保持 `SUB2API_ACCOUNT_DISPATCH_WRITES_ENABLED` 未设置或为 `0`，确认生效后再应用迁移、部署兼容版本。
2. 确认没有旧版网关实例，并使旧版调度快照失效或等待新版快照生效。
3. 在所有管理实例设置 `SUB2API_ACCOUNT_DISPATCH_WRITES_ENABLED=1`，重启后再创建“仅授权调度”账号或保存用户策略。

**不能在仍有旧版网关实例时打开写入闸门。**旧实例不识别账号隔离标记，可能将测试账号当作普通账号使用。发生问题时，先关闭写入闸门，再保留新版网关的读取和隔离逻辑；已有隔离账号或专属策略期间，不要直接回退到不识别它们的旧版网关。

## 迁移 261 与授权撤销

迁移 `261_revoke_stale_member_dispatch_grants.sql` 只删除 `origin='member'` 且已没有对应分组成员关系的授权明细，并为受影响策略递增版本。组外授权和空的指定名单策略保留。历史上已经移出后又重新加入的成员无法从现有数据可靠区分，迁移不会猜测删除。

此后移除分组成员会在同一事务撤销对应组内授权、递增策略版本；重新加入成员不会恢复旧授权。管理读取保留其他失效明细，使用 `eligible` 和 `ineligible_reason` 解释原因；保存会严格校验全部提交账号，最多 500 项，不会默默忽略失效项。

本迁移修改授权数据；升级前需备份用户、账号、分组成员关系及专属策略和明细。源码回滚脚本只能恢复源码副本，不能恢复迁移删除的授权。回退兼容镜像时，已确认失效并撤销的授权应保持撤销；若必须恢复迁移前数据，需要单独审核数据库备份，避免把失效授权重新引入。

## 编辑与调度一致性

账号编辑使用打开详情时的 ETag，一次带 `If-Match` 的 PATCH 保存账号字段与 `dispatch_scope`。凭据和 `extra` 仅提交相对编辑基线的浅层差异；412 冲突保留草稿，须显式重新加载后再编辑。主账号、影子代理、账单设置、分组绑定、授权撤销和 outbox 在事务中一起提交，提交后才刷新调度缓存。

确认失效的调度候选会被排除并继续查找健康账号，同一请求不重复尝试该候选。策略或数据库读取错误立即失败，不转入 fallback。Gemini `cachedContent` 请求只可使用缓存所属账号，并且仍须满足真实请求用户的授权；不会换用其他账号请求上游。账号的现有模型、配额、隐私和限流检查以及请求分组计费继续生效。
